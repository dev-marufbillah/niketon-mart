# Security audit — current workspace

This is a development audit, not a penetration-test certification. No production database or deployment was changed. Do not use this document as evidence of real-service or distributed-concurrency safety.

## Implemented protections

- Customer-only Google authorization-code login uses PKCE, signed short-lived state, nonce, verified email and Google's ID-token verification. It does not create staff sessions or merge guest/password identities by email. Linking/unlinking a password account requires fresh password verification and uses conditional writes plus subject uniqueness; Google sessions carry a rotatable version. Tokens are not stored. Local synthetic signed-token and single-process race tests do not certify Google Cloud, Atlas indexes or distributed link/session concurrency.
- The protected owner defaults to `marufsalauddin76@gmail.com`; server-side session checks and database write guards reject owner impersonation, demotion, disablement, deletion and identity edits. Ordinary/custom roles cannot obtain `users.manage`. Direct database operations are outside these application guards.
- Admin invitations/reset use 32-byte random tokens stored as SHA-256 hashes, expiring after 48 hours/30 minutes respectively; single-document conditional consumption prevents replay. Invitees choose their own scrypt-hashed password. Admin password reset/change and suspension rotate a session version, invalidating prior/in-flight sessions. Real email delivery has not been verified in this workspace.
- Admin and customer sessions use separate random opaque HttpOnly cookies, hashed server-side, with expiry and active-status checks. Protected pages, actions and uploads enforce server-side permissions; untrusted browser IDs/roles/prices are not authority.
- New guest order keys are random and stored hashed. Links use a URL fragment and exchange for an order-scoped HttpOnly cookie; predictable order number plus email/phone is insufficient. Signed-in access requires confirmed session provenance. Customer/review and product projections remove private data and internal prices/costs from public payloads.
- Checkout re-prices server-side and binds a customer retry key to a server-computed request fingerprint; changed or unverifiable legacy retries require checking My Orders before explicitly starting again. Invalid BDT amounts, delivery/tax rules, coupon counters and customer aggregates fail closed in the experimental transaction. Production order creation is paused. A permission-checked staff cancellation review now requires explicit coupon/customer decisions and atomically updates only eligible orders; customer self-service cancellation remains unavailable. The new Mongo transaction suite has not been run. Weight changes reconcile BDT snapshots; paid/unreconciled or incomplete historical orders are held, and higher totals require exact customer approval. Conditional order updates compare financial state.
- A read-only Mongo startup tripwire rejects known linked-main Better Auth/Mongoose records and incompatible shared-record IDs before attempting indexes. It is not exhaustive compatibility validation, migration, or a substitute for backup and restore tests.
- Gateway callbacks always return unavailable and never mark payment paid. Staff entries record separately verified payments/refunds; refunds require a paid order, separate reference and note and do not perform a transfer. The payment form does not default an unpaid order to paid.
- Uploads require permission, bounded actual request streams even without reliable `Content-Length`, decoded JPG/PNG/WebP validation, a 5 MiB file limit, re-encoding and durable Blob on Vercel. Configured Mongo failures fail closed, without silently switching to an ephemeral file database.

## Remaining risks / actions

1. Checkout, cancellation, inventory and accounting are multi-document operations and are **not production-certified**. Earlier local replica-set runs covered checkout rollback and the old cancellation hold, not the current staff-review implementation. Its rollback/concurrency tests are present but were not run in this session; real admin-action and variant-edit races, legacy Atlas BSON, multi-instance workflows, staging, and independent review remain unverified. Keep the holds. File-store CAS covers one process only and is not a distributed transaction.
2. Rate limits are in-memory per instance, based partly on proxy headers; use a shared limiter/WAF and verify trusted proxy configuration. Review CSRF/security headers, credential rotation and monitoring. Activity logging is best-effort and not tamper-proof.
3. The current reconstruction creates partial unique Mongo indexes for case-insensitive registered email, Google subject and the single featured category. Legacy invalid/duplicate identities and multiple featured flags fail closed and need a backed-up review before startup. Synthetic local Mongo tests cover competing registrations and links, but legacy Atlas data, distributed full-application workflows and customer password-change/login races still need staging review. File-driver guarantees are single-process only.
4. Old guest order records may retain plaintext keys, and legacy `?t=` URLs can leak on the initial request. Old signed-in orders without authenticated provenance require a key and are excluded from account history until trusted reconciliation. Rotate/migrate with owner approval and no history loss.
5. An optional `ADMIN_API_TOKEN` is a powerful shared bearer; leave unset unless required, restrict and rotate it. Database/Blob/mail credentials must remain server-side and never enter logs, code, ZIPs or `NEXT_PUBLIC_` variables.
6. Online payment integrations and actual refunds are absent. Do not trust manual statuses as provider-confirmed settlements or allow a gateway until official session/callback authentication, replay protection, currency/amount verification and reconciliation are implemented and tested. The form binds a submitted fingerprint to the displayed financial snapshot; focused synthetic browser checks for forged, stale, concurrent and anonymous submissions passed locally. This is optimistic concurrency, not proof of payment, a gateway, or a distributed transaction. Real staging and financial reconciliation remain necessary.
7. Review existing live currency, historic data, corporate archive and legacy owner identities after a backup and before deployment. Do not auto-convert or relabel foreign-currency history. Archive exports contain private data and must be secured.
8. An earlier `npm audit` reported eight moderate development dependency advisories. On 2026-11-23, `npm audit fix` updated the lockfile dependency tree; the latest full audit reported zero vulnerabilities, and lint passed without reported warnings. Rerun these checks before release. Investigate dev-only destination-stream errors around rapid navigation and monitor failures.

The temporary local Mongo driver and synthetic application transaction probes passed, but Atlas, Blob, Resend, gateway and distributed application tests remain outstanding. Order-index preparation is opt-in for reviewed disposable staging only; other identity/featured indexes may be created by default and startup can write data. The latest full browser attempt was not a clean pass. See `REMAINING_TASKS.md` and `docs/TRANSACTION_STAGING_BANGLA.md` for the launch gate.
