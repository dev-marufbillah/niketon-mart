# AGENTS.md — permanent project rules

These rules apply to every person and agent working on Niketon Mart, including future changes. They are not optional or limited to a particular release.

## One centralized admin, integrated in the same task

For every new **or modified** page, section, product type, preparation option, unit, service, package, feature, business function or setting, evaluate and implement the appropriate management in the **existing** centralized admin. Reuse/extend its screens, database models, repositories, server actions/APIs, navigation, role permissions, validation and activity records; do not build a second dashboard or parallel data system. Connect the storefront and persist changes. Add tests and update documentation in the same task. If a specific item is intentionally not configurable, document the reason and obtain approval rather than silently omitting the integration.

Key locations: `src/lib/admin/navigation.ts` and `resources.ts`; `src/app/admin/(panel)`; `src/lib/auth/permissions.ts`; `src/lib/catalogue`, `src/lib/repositories`, `src/lib/actions` and `src/app/api`. Admin visibility is not authorization: every protected page, API and mutation must enforce permission and account status on the server. Record security-relevant changes; the current activity logger is best-effort, not a tamper-proof audit ledger.

## Store, design and real data

- Grocery and fresh market only. Preserve the approved Niketon Mart storefront/admin design, layout and unrelated working features; do not wholesale redesign. The category rail must remain contained, independently scrollable where appropriate, and not interfere with natural vertical scrolling or the sticky header.
- Remove obsolete corporate business logic, but never permanently delete corporate or other historical data without explicit owner approval. Back up and inspect before any migration, export or cleanup; keep private archives outside releases and public paths.
- Real persistence and truthful feedback only. No invented customers, products, reviews, payment success, emails, SMS, delivery progress or business claims. Demo data is local-development-only and must never be presented as verified production records.
- Keep product/category/stock/preparation, storefront and admin connected. Shop uses the complete visible public catalogue; Fresh Market/Grocery listings and their facets use the admin-managed root navigation group, and child categories follow their current parent. The optional featured primary category (such as Dates) opens a family-scoped listing with only its own visible products and category/brand/type/price/review/stock facets; varieties are filters, not fabricated product tiles. The admin-managed `familyFiltersOnly` preference also preserves that presentation independently of the primary-nav slot; regular categories retain their existing illustrated cards by default. Clearing a filter must not leave that family, and stale or hidden explicit scopes must not broaden silently. Category images are admin-owned and shared across desktop/mobile navigation and homepage, with a real visible-product image or neutral placeholder when unset. Department headings/descriptions are managed in Settings, and a featured family's heading/description comes from its category record. Standard English navigation labels stay fixed, with Categories immediately after Shop and About Us last after the featured slot; Blog stays in the footer. Counts and options derive from the current public catalogue, never hardcoded category-to-product mappings. The user-requested Dates and example variety taxonomy is seeded only in a fresh local demo database, without date products, prices or stock; existing and production data must never be changed automatically. Do not create hardcoded category/product lists, storefront links to nonexistent categories, or a second admin.
- Keep desktop cards and banners contained and product details usable without oversized images. On small screens preserve the existing layout apart from the requested hero image-before-text order. Product card surfaces must remain real keyboard/middle-click-capable links; cart and wishlist controls must remain independent and sold-out/choice rules must be respected.
- Render-only deduplication must not create a shared stale catalogue/settings cache or serve cached reads to mutations. Verify that admin edits appear on later requests. Measure navigation changes in comparable production builds; do not claim a live speedup from unrepresentative development timings.
- Enforce applicable choices and prices server-side; snapshot product, preparation, charges, units, weight and other order facts so later edits do not rewrite history. Expose only allowlisted public product/review fields; never leak supplier costs, margins or private records in HTML, React payloads or APIs.
- Use numeric **BDT/৳**, central formatting (`src/lib/utils/currency.ts`) and Bangladeshi lakh grouping. Never infer, convert or merely relabel historical foreign-currency amounts as BDT. Any conversion requires backup, explicit approval and a reviewed reconciliation plan.

## Checkout, privacy and payments

- Production checkout is deliberately **paused**. Online cancellation is held in **all** environments: the owner selected manual review for coupon orders and customer totals that cannot be safely confirmed. Do not infer a coupon-release or aggregate-accounting policy. There is no completed in-app staff-review/refund workflow yet. Do not remove holds until a permission-checked review workflow and transactionally safe order/stock/coupon/customer/ledger writes, idempotency and cancellation are implemented and tested against real MongoDB with concurrent instances and failure injection. The local file store is for development; its same-process CAS is not a distributed transaction.
- The Vercel-linked GitHub `dev-marufbillah/niketon-mart` `main` inspected at `892500c4d5a335dd34ecbc9ee5680f26f40dd944` is a substantially different Better Auth/Mongoose codebase. A read-only Mongo compatibility tripwire rejects known foreign collections and incompatible shared-record IDs before index creation, but cannot certify a database safe. Do not start this app on that live database, overwrite `main`, or migrate records without a private backup/restore test, reviewed mapping and explicit approval. Preserve unrelated remote features and corporate history; see `docs/GITHUB_MAIN_COMPARISON.md`.
- Never trust browser-supplied prices, tax, discount, totals, quantities, preparation charges, customer IDs or roles. A variable-weight increase requires the customer's exact approval; reductions and discounts must reconcile against the stored checkout snapshot. Do not re-price paid, unreconciled or insufficiently snapshotted historical orders.
- Online gateway code is an unimplemented scaffold: credentials alone do not enable it. Never simulate payment or refund. Manual entries record an independently verified real-world event and do not transfer money. Never collect/store card number, CVV, PIN or OTP.
- Customer/admin credentials and sessions are separate even though sign-in is shared. Only a successful server-verified active staff credential grants staff access; customer signup or matching an email never grants it. Clear old sessions when switching identities and bind the staff shopper profile by verified admin ID, never by email. Require a shopper session for product details, cart/wishlist/checkout and their server actions; keep public catalogue/search and existing private guest-order links usable. Scope persisted shopping data to the authenticated identity; never silently claim old guest lists or orders.
- Google OAuth is customer-only: verify Google signature, issuer, audience, expiry, nonce, verified email, PKCE and state server-side. Identify the customer by the immutable Google subject hash, not by email; never automatically merge a password/guest/staff record. Connecting an existing password customer requires its active session, fresh password verification and matching verified Google email. Disconnect rotates the Google session/link versions. Do not persist Google tokens. Keep credentials server-side in ignored environment configuration, not in an admin/browser field; existing Customers permissions/status/session management and activity events apply. Review the Google subject unique index and live provider flows before production.
- A predictable order number, email or phone alone must never unlock private orders. Use an authenticated owner or a high-entropy private key; new keys are hashed at rest and passed in a URL fragment before exchange for an order-scoped HttpOnly cookie. Do not log access/setup links. Legacy query links/plaintext keys require a reviewed migration.
- Images require authorization, bounded request parsing, real image validation and durable storage; on Vercel require Blob. Never store Base64 data or rely on Vercel's ephemeral local filesystem.

## Quality and deployment gate

Run `npm run typecheck`, `npm run test:unit`, `npm run lint`, `npm audit` and an isolated `npm run build`. Exercise browser regressions only against a fresh disposable store with the test handshake; see `REMAINING_TASKS.md`. Test desktop/tablet/mobile and relevant server-side permission/tampering cases. Report exact results and untested real services; do not claim distributed concurrency, actual email, Blob or gateways work based on a local mock.

Git push to the approved, inspected branch must happen before any Vercel deploy or settings change; never force-push or assume reconstructed source matches remote. Never deploy or mutate an unknown live database without a verified backup, currency/identity review, migration plan, staging tests and explicit owner approval. Do not commit secrets, `.data`, private uploads, archives, dependency folders or build artifacts. Review `REMAINING_TASKS.md` before any launch.
